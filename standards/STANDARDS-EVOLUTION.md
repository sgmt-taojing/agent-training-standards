# 规范自进化机制（Standards Self-Evolution）

> 2026-08-10 确立 · 用户指令：「找规范自进化」
> 对标 hermes-evolution：让 ASH 训练规范 + 能力包知识卡 + 行业知识库自身能进化。
> **核心原则：规范不是静态文档，而是活的——使用即进化、反馈即升级、审批才落地。**

---

## 一、进化对象（4 类资产，各有进化环）

| 资产 | 文件 | 进化触发 | 版本管理 |
|---|---|---|---|
| 训练规范 | `standards/AGENT-TRAINING-STANDARDS.md` | 规范条款被反复违反/行业标准更新/新章节建议 | semver（major=破坏性改版） |
| 能力包知识卡 | `knowledge-cards/*.json` | 能力包升级/资产变更/边界调整 | 随包 semver 联动 |
| 行业知识库 | `data/industry-kb.json` | 新行业条目/合规变化/评测指标更新 | semver（minor=新增行业） |
| 能力包注册表 | `capability-registry.json` | 新包注册/版本同步/计费调整 | 随包联动 |

## 二、进化信号（3 级，对标 hermes-evolution 强/中信号）

### 强信号（直接触发进化提案）
- 评估/实战中发现规范条款被**反复违反**（≥3 次）→ 条款需修真
- 行业法规/标准变更（如新法规出台）→ 合规条款需更新
- 能力包资产实际指标与知识卡声明**偏差 ≥10%** → 质量门槛需校准
- 用户/客户明确要求新增规范维度或行业条目

### 中信号（2 个以上触发进化提案）
- 同类问题在多个能力包中重复出现 → 抽象为通用规范条款
- 使用日志显示某规范条款**从未被引用/触发** → 可能冗余需精简
- 能力包进化（capability-evolve.sh bump）后知识卡未同步

### 弱信号（仅记录，不触发）
- 单次偏离（可能偶发）
- 主观偏好（无客观证据）

## 三、进化环（PDCA 闭环）

```
 ┌─── 收集信号 ───→  ┌─── 评估门槛 ───→  ┌─── 提案草稿 ───→  ┌─── 审批 ───→  ┌─── 落地 ───→  ┌─── 版本发布 ───┐
 │                │                │                │                │                │                │
 │ ·使用日志       │ ·强信号→必过     │ ·写 draft 到     │ ·用户审批       │ ·更新目标文件   │ ·semver bump   │
 │ ·反馈聚合       │ ·中信号≥2→过     │   evolution-     │ ·rejected→     │ ·同步关联资产   │ ·CHANGELOG     │
 │ ·评估报告       │ ·弱信号→不过     │   drafts/        │   记录+跳过     │ ·触发重生成     │ ·公网重发      │
 │ ·法规监控       │ ·去重检查         │   pending/       │ ·approved→落地  │                │                │
 └────────────────┘ └────────────────┘ └────────────────┘ └────────────────┘ └────────────────┘ └────────────────┘
```

### 各阶段执行规范

**① 收集信号**
- 使用日志：能力包 `packs/<id>/usage/*.jsonl`（调用记录）
- 反馈聚合：`data/assessments.jsonl`（客户评估记录）+ `data/billing/usage.jsonl`（调用计量）
- 评估报告：各包 EVOLUTION.md 中的修真记录
- 法规监控：定期 web_search 行业法规更新（cron 触发）

**② 评估门槛**
- 强信号：必过（违反 ≥3 次 / 法规变更 / 偏差 ≥10% / 用户明确要求）
- 中信号：≥2 个同类才过
- 去重检查：同签名 pending 草稿存在 → 更新不新建；最近 30 天 rejected 且无新证据 → 跳过
- 门槛不通过 → 记录但不动（避免噪音）

**③ 提案草稿**
- 草稿路径：`evolution-drafts/pending/<signature>.md`
- 草稿内容：变更类型 / 证据 / 拟改条款 / 影响范围 / 回滚方案
- **禁止直接改目标文件**（与 hermes-evolution 一致）

**④ 审批**
- 用户审批 approved → 落地
- 用户审批 rejected → 记录签名 + 日期，30 天内同类不再触发
- 超时（7 天）未审批 → 自动过期清理

**⑤ 落地**
- 训练规范：edit `AGENT-TRAINING-STANDARDS.md`
- 知识卡：重跑 `gen-knowledge-cards.js`
- 行业知识库：edit `data/industry-kb.json`
- 注册表：edit `capability-registry.json`

**⑥ 版本发布**
- 规范 semver bump（patch=条款修真 / minor=新增维度或行业 / major=破坏性改版）
- 能力包版本同步 `capability-evolve.sh`
- CHANGELOG 追加
- 公网重发 `publish-github.sh`

## 四、自动化触点

| 触点 | 触发条件 | 动作 |
|---|---|---|
| **周评估 cron** | 每周一 09:00 | 扫描上周使用日志 + 反馈 → 信号收集 → 有强信号则生成提案草稿 |
| **能力包 bump 联动** | capability-evolve.sh 执行后 | 检查知识卡是否需同步重生成 |
| **法规监控 cron** | 每月 1 日 10:00 | web_search 行业法规更新 → 有变更则生成合规条款进化提案 |
| **评估闭环** | 每次需求引擎 analyze 调用 | 检查是否触发新行业条目需求（客户行业不在 12 行业中 → minor 进化提案） |
| **偏差检测** | 评估/实战中指标偏差 ≥10% | 强信号 → 质量门槛校准提案 |

## 五、草稿模板

```markdown
# 规范进化提案：<标题>

## 变更类型
[ ] patch（条款修真） [ ] minor（新增维度/行业） [ ] major（破坏性改版）

## 证据
<信号来源：使用日志/反馈/法规变更/偏差检测>

## 拟改条款
<原文 → 新文（精确到章节号）>

## 影响范围
<受影响的能力包/行业/章节>

## 回滚方案
<版本回退策略>
```

## 六、进化日志（审计可追溯）

- 规范进化记录：`evolution-drafts/changelog.jsonl`（全量流水：提案/审批/落地/发布）
- 能力包进化记录：各包 `EVOLUTION.md`
- 行业知识库变更：`data/industry-kb.json` 的 `updatedAt` 字段 + CHANGELOG

## 七、安全约束（红线）

1. **审批落地制**：无审批不落地（与 hermes-evolution 一致）
2. **去重防噪**：同签名 pending 不新建；30 天内 rejected 不重提
3. **空转保护**：无信号/无证据不触发（与 capability-evolve.sh 一致）
4. **版本可回滚**：每次 major 改版前备份上一版到 `archive/standards/`
5. **公网同步**：落地后必须重发公网（publish-github.sh），保证公网与本地一致
